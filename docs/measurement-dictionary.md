**Status:** Provisional 0.1.0-draft

**Effective for pilot use:** 2026-08-09

**Next review:** 2027-02-09

**Control source:** [Repository Health Control Catalog](control-catalog.md)

## 1. Measurement rules

### 1.1 Assessment grain and clock

- `T` is the assessment timestamp in UTC.
- A **deployable unit** is the smallest independently released, deployed, applied, published, or retired output. Measure each unit first. A single-output repository has one unit.
- The default event window `W90` is `[T - 90 days, T]`. If fewer than five eligible events exist, extend to `W365 = [T - 365 days, T]` and label the result **Low Sample**. For a repository classified as stable-supported or otherwise legitimately low-activity, if W365 still has fewer than five events, extend a health metric to the last representative completed change/release cycle even when it is older than W365, provided the relevant contract and control have not materially changed. Label the result **Historical/Low Sample**, report the most recent included event's age in days, and pair the historical result with current configuration and current-state evidence. If no representative event exists, report **No Events** with current state; absence alone is not a failed event and events must never be fabricated. A control can remain Unknown when its own evidence minimum requires an actual demonstration that does not exist.
- A **current-state** measure evaluates the exact state at `T`; a **trend** measure evaluates events or duration in its window.
- All durations use elapsed wall-clock time. Ratios are reported as percentages to one decimal place, while threshold comparisons use the unrounded value.

### 1.2 Repository vocabulary

- **Main:** the declared primary integration branch, regardless of its literal name.
- **Critical ref:** Main plus every production, release, maintenance, environment, GitOps, or release tag/ref whose unauthorized update, deletion, or rewrite could change, misrepresent, prevent recovery of, or break lineage to a current supported output or an archived preserved state.
- **Eligible change:** a final revision accepted into Main or another critical ref during the window. Initial repository import is excluded only when labeled as such and followed by an enforced baseline; bot changes are included unless a documented trusted-robot rule applies.
- **Eligible release:** a deployment, publication, package/model/data release, infrastructure apply, or content publication that changed an output during the window.
- **Required check/category/assertion:** an item declared applicable by the version-controlled policy, risk profile, or this standard.
- **Successful:** a terminal, non-neutral result that the enforcing system recognizes as satisfying the requirement. Skipped, cancelled, timed out, neutral, or stale results are not successful unless the policy explicitly defines a safe path-specific N/A before the run.
- **Fresh evidence:** evidence meeting the limits in section 1.4 and the metric row.
- **Cadence contract:** the owner-approved normal integration, release-train, maintenance, publication, or reconciliation interval for a profile, expressed in elapsed days with rationale, owner, approval date, and branch/fix/cleanup SLOs stated both in days and as a multiple of that cadence. If at least five comparable completed events exist in W365, the observed median interval is also reported; the declared cadence is not silently replaced by it.

### 1.3 Evidence-source codes and precedence

| Code | Evidence source | Examples |
|---|---|---|
| FORGE | Source-control platform | refs, protections, rulesets, PR/MR, reviews, merge/push events |
| REPO | Content at the assessed revision | manifests, policies, README, workflow files, ownership metadata |
| CI | Build/validation system | run, job, check, artifact, timing, retry metadata |
| DEPLOY | Deployment/publication control plane | environment state, deployed revision, approvals, status/history |
| ART | Artifact/package/content registry | digest, version, immutability, provenance, SBOM |
| IAM | Identity and audit systems | members, roles, MFA, privileged and bypass events |
| SEC | Security systems | secret, dependency, vulnerability, workflow-security findings |
| PORT | Portfolio/service catalog | owner, lifecycle, criticality, authoritative URI, dependencies |
| OPS | Operational systems | runbook verification, recovery exercise, incident and monitoring evidence |

When sources disagree, runtime/registry identity (`DEPLOY`/`ART`) takes precedence for what is deployed, `FORGE` takes precedence for effective source-control enforcement, and exact-revision machine evidence takes precedence over prose. A conflict is reported explicitly and the affected current-state metric is **Unknown** until reconciled.

### 1.3.1 Evidence-state layers

Assessment records keep these four evidence layers distinct. Evidence at one layer does not, by itself, prove a claim at another layer.

| Layer | What it can establish | What it cannot substitute for |
|---|---|---|
| **Source/working state** | Files, generated differences, validation output, or an uncommitted working tree captured at a stated location and time. | It does not prove that the content was committed, pushed, accepted into Main, released, or deployed. |
| **Committed/pushed state** | An immutable Git commit, its reachability from a named ref, and—when observed from the authoritative remote—that it was pushed and retained there. | A repository commit or tag does not prove a successful build, immutable release, publication, or current production state. |
| **Release evidence** | A build, package, provenance, approval, promotion, publication, or release record binding an immutable source revision to an immutable artifact/content identity and terminal event status. | A release record does not prove that the identified output is the state currently running or published unless current target evidence also establishes that fact. |
| **Observed production state** | A fresh observation from the deployment, runtime, reconciler, registry, or publication control plane identifying the output currently active at `T` and its terminal status. | A mutable label such as `main`, `latest`, an environment name, or a version string without immutable artifact/content and source linkage does not prove source correspondence or G-02. |

A single authoritative record may support more than one layer only when it independently contains the required identities, status, timestamps, and freshness for each claim. Otherwise the unproved layer is **Unknown**; assessors must not infer it from a neighboring layer or from a person's recollection.

### 1.4 Freshness and evidence coverage

Unless a metric is stricter:

- FORGE, CI, DEPLOY, ART, IAM configuration/current-state extracts: captured no more than 24 hours before `T`.
- Event extracts: complete through no earlier than 24 hours before `T` and cover W90, W365, or the documented Historical/Low Sample extension in section 1.1 as applicable.
- SEC secret/dependency/vulnerability scan: no older than 7 days for Baseline/Elevated and 72 hours for Critical.
- REPO evidence: read from the exact assessed Main SHA.
- PORT extract: no older than 30 days and confirmed within 365/180/90 days for Baseline/Elevated/Critical.
- Documentation-route verification: within 365/180/90 days for Baseline/Elevated/Critical.

For event ratios, evidence coverage is `classifiable eligible observations / all enumerated eligible observations × 100`. A metric is Unknown when coverage is below 90% Baseline, 95% Elevated, or 100% Critical. Missing observations never enter the numerator. For every ratio, approved N/A observations or assertions are removed from both numerator and denominator and retain their rationale; exceptions never remove observations or assertions.

### 1.5 Aggregation

1. Calculate each metric per deployable unit.
2. Current-state and control-assertion metrics aggregate by logical AND: the repository meets the threshold only when every applicable unit does.
3. Event ratios also publish the micro-average `sum(numerators) / sum(denominators)`, but the repository control result is the **worst threshold band** of any applicable unit. This prevents a high-volume healthy unit from hiding a failing low-volume unit.
4. Latency metrics publish per-unit p95 and repository pooled p95; the control result is the worst per-unit threshold band.
5. A documented N/A unit is excluded. An Unknown applicable unit makes the repository metric Unknown; known per-unit values remain visible and the scoring rubric governs the resulting conformance and assurance.
6. Do not average dimension percentages into DORA outcomes, and do not include DORA outcomes in the repository-health score.
7. A control with multiple linked health metrics is scored once, using the combination rule in its catalog record; linked metrics never become extra control points. Specifically, SPI-01 uses the worst applicable band across M-SPI-01 and M-SPI-01T, and SPI-02 uses the worst applicable band across M-SPI-02S and M-SPI-02. A documented `No Events` trend/rate carries the paired current-state band. G-01 is determined only by M-SPI-01, and G-02 only by M-SPI-02S.

### 1.6 Trend-series rules

When a row requires a named trend, calculate the same row formula at each specified snapshot and publish the ordered `{timestamp, numerator, denominator, raw_value, band}` series, the first-to-last absolute percentage-point change, and the count of adverse band changes. A **90-day trend** uses weekly snapshots at `T - 84, -77, …, -7, T`; a **quarterly trend** uses the last four completed calendar-quarter ends plus `T`; a **monthly trend** uses the last twelve completed calendar-month ends plus `T`. Historical snapshots require contemporaneous retained evidence or deterministic reconstruction from complete events; an unreconstructable snapshot is `Unknown`, is not imputed, and makes the trend incomplete. Trend values do not independently change the control band unless its catalog threshold expressly says they do.

### 1.7 Measurement integrity and anti-gaming

- Owner-approved cadence contracts and SLOs must be prospective, versioned, effective-dated, and justified by the operating cadence. Each event is evaluated against the version effective when the event occurred; an SLO selected or changed after results are known cannot relabel prior events.
- When at least five comparable intervals exist in W365 or the Historical/Low Sample extension, compare the declared interval with the observed median. An unexplained ratio above `2.0` or below `0.5` is a material declared-versus-observed contradiction, not permission to choose the more favorable interval.
- Eligible populations come from the metric definition and a complete authoritative inventory established before numerator classification. Events, units, refs, releases, findings, paths, or assertions cannot be omitted to improve a denominator; only a pre-defined, evidenced N/A rule removes an item from both numerator and denominator.
- Data suppression, selective retention, or inability to enumerate the eligible population makes the affected observation or metric **Unknown** under the coverage rule. An exception records accepted risk and never cures population or denominator integrity.

### 4.1 Profile tests for M-CGD-05

| Declared profile | Conforming event tests |
|---|---|
| **Trunk-based** | Work integrates to Main within the owner-approved integration SLO expressed relative to the cadence contract; active work-in-progress limits are declared; no separate long-lived integration branch exists; release branches are late-cut and receive fixes from Main. |
| **GitHub Flow/short-lived feature branches** | A short descriptive branch proposes one coherent change to Main through a reviewed/validated change; branch lifetime and post-merge cleanup meet owner-approved SLOs expressed relative to integration cadence; production policy is declared separately. |
| **GitFlow** | Feature branches originate from and return to `develop`; release branches originate from `develop` and return to both Main and `develop`; hotfixes originate from Main and return to Main and `develop`; production releases on Main are tagged. |
| **Environment-branch flow** | Features and fixes enter Main first; commits promote downstream through declared environment refs; promotion direction, dwell time, and emergency reconciliation meet owner-approved cadence-relative SLOs. |
| **Release train/multi-version maintenance** | New work enters the declared integration line; release cuts follow the declared train cadence; fixes originate there and are deliberately backported within owner-approved support-cadence SLOs; active release/version refs remain protected and EOL refs are retired. |
| **GitOps promotion** | Desired state is declarative, versioned and immutable, pulled automatically, and continuously reconciled; promotion changes an authorized ref/path/artifact identity, and drift detection/reconciliation meets the owner-approved reconciliation cadence/SLO. |
| **Fork/integration-manager** | Contributions originate outside the canonical repository, enter through an attributable proposal/patch, and are accepted only by authorized integrators into canonical Main; integration and contributor-ref disposition meet owner-approved cadence-relative SLOs. |
| **Direct gated trunk** | Direct Main updates are small, attributable, and pass declared pre-submit authorization, review/equivalent, and validation controls; no uncontrolled push is conforming, and submission/repair SLOs are expressed relative to integration cadence. |
| **Custom/hybrid** | The approved profile supplies testable origin, target, lifetime, promotion/reconciliation, fix-direction, cleanup, and EOL rules plus owner-approved cadence-relative SLOs. A custom label alone is insufficient. |

## 10. DORA delivery outcomes — separate, informative panel

These five measures follow the current DORA model and are **not** controls, dimension inputs, grade modifiers, or tie-breakers. Report them per application/service and as trends; do not compare dissimilar repositories or teams. Use W90, extend to W365 only for Low Sample, and display sample size. The health-control Historical/Low Sample substitution in section 1.1 does not create current DORA outcomes.

| ID | Exact definition | Unit/window | Missing data and aggregation |
|---|---|---|---|
| **DORA-CLT** Change lead time | For each production deployment change, `successful production deployment timestamp - first commit timestamp of that change`; report median and p85. | Hours/days, W90. | Requires commit-to-deployment linkage. Unknown linkage is reported as coverage; do not impute. Report per service, not repository aggregate. |
| **DORA-DF** Deployment frequency | `count of successful production deployments / observable calendar time`; report deployments per day/week/month and median interval. | Count/rate, W90. | No reliable production deployment inventory = Unknown. Multiple deployable units remain separate services. |
| **DORA-FDRT** Failed deployment recovery time | For each deployment requiring immediate intervention, `time service was restored to intended level - time failure began`; report median and p85. | Minutes/hours, W90. | No failed deployments = No Events, not zero recovery time. Incident/deployment linkage required. |
| **DORA-CFR** Change fail rate | `production deployments requiring immediate intervention / all production deployments × 100`. | Percent, W90. | No deployments = No Events. Unknown intervention classification is reported as coverage and not imputed. |
| **DORA-DRR** Deployment rework rate | `unplanned production deployments made to address a prior deployment defect / all production deployments × 100`. | Percent, W90. | Requires planned/unplanned and causal classification. No deployments = No Events. |

## 11. Assessment output requirements

Every reported metric must include:

1. Metric and catalog version.
2. Assessment timestamp, repository URI, exact Main SHA, deployable unit, repository type, risk tier, and declared methodology.
3. Numerator, denominator, raw value, threshold band, sample size/window, and evidence coverage.
4. Source systems and capture timestamps.
5. Unknown, N/A, Low Sample, conflicts, and exceptions as separate fields.
6. Per-unit result plus repository aggregation rule used.
7. For current-state metrics, the exact identities evaluated.
8. For DORA, an explicit `informative_only: true` marker and no repository-health score contribution.
9. The metric question, eligible population, polarity, limitations, and registered source IDs from section 12.

No metric in 0.1.0-draft authorizes automated enforcement or repository mutation. This dictionary specifies evidence and calculation only.
